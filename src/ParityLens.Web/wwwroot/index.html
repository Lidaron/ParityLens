Overview

What Parity Lens does

Parity Lens runs the same public SDK operation in a baseline and a candidate. It records which functions ran, what each function received and returned, what HTTP request each SDK built, and how each SDK handled the response.

Equal final JSON is not enough.

An SDK can return the expected value after sending the wrong header, taking the wrong fallback path, or hiding an error. Parity Lens keeps the calls and intermediate values visible, so a matching result cannot hide a different implementation.

Run the same callGive both SDKs equivalent inputs and the same response bytes.
Look insideCompare nested calls instead of checking only the final return value.
Keep native namesShow each SDK's real paths and symbols while comparing mapped fields.
Test failures tooUse scenarios such as JSON 404, IIS 404, and HTTP 503.
A match has a clear limit. It applies to the operation, versions, input fixture, and scenario you ran. It says nothing about inputs you did not run.

Trace capture

How a trace is captured

The SDK still runs its production code. An annotation marks each function worth comparing. C# IL weaving and Rust proc macros record when that function starts and ends, which traced function called it, which selected values crossed the boundary, and whether it succeeded.

Public operationCall the real SDK API
AnnotationsMark functions to record
Nested spansCapture parent and child calls
HTTP sendReturn fixture bytes
Trace bundleReturn calls and values
  1. 1
    The harness calls both SDKs

    Each side gets equivalent typed inputs and the same response scenario.

  2. 2
    The wrappers record nested calls

    A stack records the call ID, parent ID, depth, order, elapsed time, and result.

  3. 3
    The wrappers record selected values

    You choose which inputs are safe. Outputs keep objects, arrays, nulls, enums, exceptions, and diagnostics.

  4. 4
    The transport catches the final HTTP request

    Production code has already built the request. The test transport checks it and returns the scenario bytes.

  5. 5
    Parity Lens compares the two traces

    Mappings line up equivalent names. Unmapped names and all native symbols remain visible.

Do not mock business functions or build response objects by hand. Both shortcuts skip the code you need to compare.

Mappings

Why mappings exist

C# and Rust often use different names for the same value or function. A mapping gives those names one ID for comparison. It does not rename either SDK. Function I/O still shows the original path and symbol from each side.

Functions

Pair the full method and function names. Their shared ID places both calls on one trace row. Parent IDs and call order keep the call tree intact.

C#: Sdk.Executor.ExecuteAsyncRust: sdk::executor::execute
Named fields

For a class or struct, pair its full type name and a path relative to that type. The mapping then works everywhere that type appears.

QueryOptions<T> + $["select"]
Dynamic fields

Dictionaries, tuples, and untyped JSON have no stable declaring type. Pair them by function, input or output direction, and full path.

deserialize + output + $["id"]
Enums

Pair the full enum type names, then pair their members. Reflection and Rust macros supply the numbers.

LegacyDN = LegacyExchangeDN
  • Explicit field mappings should include both C# and Rust endpoints.
  • Pair the object, array, or leaf that you want to compare as one unit.
  • Parity Lens keeps an unmapped property under a json: ID, so it does not disappear.
  • An excluded field does not affect comparison, including when its value, presence, type, or shape changes.
  • One compiled symbol can belong to only one mapping.

Setup

Choose functions to trace

Annotations are not limited to public API methods. A complete integration must trace the public operation that the harness calls, request construction, request execution and resilience, the final HTTP send, and response mapping. If one function owns several stages, one annotation can represent those stages. If a stage does not exist in one SDK, keep the other SDK's call visible as an unpaired boundary.

Trace boundaryC# placementRust placement
Public operationParityTraceFunction on the concrete request methodThe concrete operation method inside its impl block
Internal callsEach concrete executor, converter, transport, or response method to compareEach concrete request, executor, transport, or response method to compare
Traced dataParityTraceData on SDK classes and structstrace_data on SDK structs and trace_enum on supported enums
Annotate boundaries, not every helper. Add a function annotation when its input, output, success state, order, or parent relationship belongs in the parity trace. Do not annotate private calculations that add no comparison value.
Use one shared IDUse request.execute, not a line number or generated span ID.
Keep the compiled nameRecord the full implementation function name on each side.
Choose inputsList safe parameters. Redact tokens, cookies, and credentials.
Function IDs do not control timeline behavior.

http.send is the current shared ID for the final send call, but it is not reserved. The function with role: "serviceBoundary" places the server endpoint icon after that call. Exactly one shared function must have this role.

Share the step ID, not parameter spelling. Corresponding boundaries use the same ID. C# can use [ParityTraceFunction("request.execute", "requestData")] while Rust uses #[trace_function("request.execute", "request")]. Each selected name must match its own method. A boundary that exists in only one SDK may keep a language-specific ID and remain unpaired.
B2
Trace format

Write one trace record per call

Record each function after it returns or throws. Include its parent, call order, elapsed time, selected inputs, output, success flag, and compiled names. Parity Lens reads this JSON shape.

trace-bundle.json
{
  "traces": [{
    "stepId": "find-by-key",
    "functionName": "sdk::users::find_by_key",
    "spanId": "42",
    "parentSpanId": null,
    "depth": 0,
    "sequence": 42,
    "input": { "key": "avery@contoso.test" },
    "output": { "value": { "id": "user-001" } },
    "durationMs": 7,
    "isSuccessful": true,
    "symbols": {
      "functionSymbol": "sdk::users::find_by_key",
      "parameters": [{
        "name": "key",
        "typeSymbol": "sdk::DirectoryKey",
        "path": "$[\"key\"]"
      }],
      "outputTypeSymbol": "sdk::Response<sdk::User>"
    }
  }],
  "outgoingHttpRequests": 1
}
Keep a stack for each call. When one traced function calls another, the child must record its parent's span ID and its own depth.
B3
HTTP fixture

Swap only the final HTTP sender

Run the public SDK API. Keep its routing, request builders, retry and fallback code, executor, and response parser. Replace only the component that would send bytes over the network.

  1. 1
    Receive the request

    Record the method, URI, headers, and raw body that the SDK produced.

  2. 2
    Check the request

    Stop the test if it does not match the operation fixture.

  3. 3
    Return exact response bytes

    Keep the status, HTTP version, headers, content type, and body unchanged.

Do not mock the SDK method, request builder, or response parser. A mock skips the code you are trying to compare.
C#
C# setup

Annotate every concrete method boundary

For each required C# trace boundary, put one ParityTraceFunction attribute on the concrete method body. This includes public operations and internal methods such as the request builder, executor, HTTP client, and response deserializer. Fody injects entry, completion, and exception hooks into the compiled IL.

ItemClient.cs
[ParityTraceFunction("items/read-item", "id")]
public async Task<ItemResponse> ReadAsync(
    string id,
  CancellationToken cancellationToken = default)
{
  // Production implementation
}
  • Annotate the implementation method. Interface metadata alone has no method body to weave.
  • Use one attribute per method. The build weaver injects its boundary hooks once.
  • Check every selected input name. An unknown name is silently omitted from the trace.
  • Do not select credentials or cancellation tokens. Mark SDK-owned boundary types with ParityTraceData.
Example internal boundary. An internal executor can use [ParityTraceFunction("request.execute", "requestData")]. It is not a public SDK operation, but it must be annotated when request execution is part of the trace.

C#
C# setup

Collect traces with a sink

Open an ambient ParityTraceSession around the public SDK call. Build-time weaving instruments annotated methods, so callers use the SDK directly and the SDK does not own a sink or tracing context.

TraceSink.cs
sealed class TraceSink : IParityFunctionTraceSink
{
    private readonly object gate = new();

          public List<ParityFunctionTrace> Traces { get; } = new();

          public void OnFunctionTrace(ParityFunctionTrace trace)
    {
        lock (gate)
            Traces.Add(trace);
    }
}

var sink = new TraceSink();
        using ParityTraceSession session = ParityTraceSession.Start(sink);
        await client.ReadAsync("item-1", cancellationToken);
The woven boundary records a trace after the method returns or throws. Sink failures are observational and do not affect SDK calls. Keep OnFunctionTrace short and thread-safe.
Concurrent operations may share a context, but a shared sink must synchronize its trace collection.
C#
C# requirements

Read names from compiled types

Use reflection instead of typing names into configuration. Record the implementation method, declaring type, selected parameter types and paths, output type, and public property names.

  • Resolve the implementation method through GetInterfaceMap.
  • Use Type.FullName for the CLR type name.
  • Add serializers for HTTP values, exceptions, enums, and query options.
  • Redact authorization, cookies, secure tokens, and other credentials before serialization.
  • Verify successful, faulted, synchronous, Task, and Task<T> methods that you annotate.

Rust setup

Annotate traced methods and their data

Put trace_function on the concrete impl method for every required Rust boundary, whether public or internal. Typical targets are the public operation, request context, executor, transport, and response mapper. Use the data macros on SDK-owned types that cross selected input or output boundaries.

items.rs

        &self,
            id: &str,

}

Rs
Rust requirements

Make traced values serializable

  • The first trace_function argument is a non-empty string. Every later string must be the exact identifier of a method parameter.
  • Selected input types must implement serde::Serialize. The resolved future output must implement both Serialize and FunctionTraceOutput.
  • Use trace_data instead of adding a second Serialize derive. Add serializer functions for foreign types that need adapters.
  • trace_enum does not support data-carrying variants or flags. Its generated metadata reports enum_flags as false.
  • Automatic adapters redact SecureToken and credential headers in recognized fields. Audit and omit any other secret-bearing input.
capture.rs
let capture = parity_lens_trace::capture(
          parity_lens_trace::TraceOptions::default(),
          client.read("item-1"),
        ).await;

        let output = capture.output;
        let traces = capture.traces;

assert!(!traces.is_empty());
assert_eq!(transport.send_count(), 1);
The capture scope is Tokio task-local, so concurrent SDK operations keep independent parent stacks and trace collections.
Keep manual trace calls out of production function bodies. The annotations wrap existing behavior and preserve normal return and error semantics.

Rust bridge

Return Rust traces through the C ABI

The caller owns the output buffer. On the first call, build the trace JSON and return its byte count. On the second call, copy those bytes into the supplied buffer.

NativeTraceBridge.cs
nint required = CaptureOperationTrace(
    input, (nuint)input.Length, null, 0);
        if (required < 0)
          throw new InvalidOperationException($"Trace capture failed: {required}");

var output = new byte[checked((int)required)];
nint written = CaptureOperationTrace(
    input, (nuint)input.Length,
    output, (nuint)output.Length);
        if (written < 0 || written > (nint)output.Length)
          throw new InvalidOperationException($"Trace read failed: {written}");

var bundle = JsonSerializer.Deserialize<TraceBundle>(
    output.AsSpan(0, checked((int)written)));
Keep the two calls together under one lock. The first call stores pending JSON; the second consumes it. Treat every negative return as a status code for bad input, an unsupported call, a small buffer, or an execution failure.
